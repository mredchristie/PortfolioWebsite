Self-Hosted Infrastructure

20 containers, a mail server and a VPN on one 2 GB droplet, and the parts that cannot afford to go down with it moved out to the edge...

0111. The Architecture

Almost everything on this page runs on a single DigitalOcean droplet in London with 2 GB of RAM, deliberately kept small and cheap. A host nginx terminates TLS for every subdomain and proxies to containers bound to localhost, while the mail server and VPN take their traffic directly.

Two things sit deliberately outside it, both on Cloudflare. The portfolio site you're reading is static, mirrored to an R2 bucket, so it stays up even when the droplet doesn't. The Cornish Water Watch API runs on a Worker backed by D1, because its collector has to fire every fifteen minutes for years without missing a window - and a box that is also carrying a mail server is the wrong place to promise that.

1000. What's Running

Email, Run Myself

I run my own mail server rather than renting a mailbox from Google, so anything addressed to @mredchristie.dev lands here. One program does all of it: sending, receiving, and a webmail client to read it in.

The hard part isn't running it, it's being believed. Mail from a server nobody has heard of gets treated as spam by default, so the domain publishes a set of public records that let the receiving end check the message genuinely came from me and hasn't been tampered with. DigitalOcean also blocks the standard outgoing mail port, to stop their customers being used to send spam, so outbound mail hands off to a relay service while incoming mail arrives here directly.

The Front Door

Every subdomain - the weather app, the surf forecast, all of them - arrives at the same machine on the same address. nginx is the doorman: it reads which name you actually asked for and hands you to the right app.

It also handles the padlock in the address bar. All 11 subdomains have their own certificate, issued free and renewed automatically well before it expires, because a certificate that quietly lapses takes the site down just as effectively as the server failing. The apps behind it can only be reached from inside the machine, so the door is the only way in, and putting a new service up is one config file and one DNS record.

nginx certbot Let's Encrypt

A VPN of My Own

A private tunnel into the server. On a cafe or airport network, my traffic comes out of my own machine in London instead of whatever the Wi-Fi provider feels like doing with it, and it's how I reach the admin pages that aren't open to the public at all. Adding or revoking a device is a click on a web page rather than editing config by hand.

WireGuard wg-easy Docker

The Apps Themselves

Each project ships as a set of containers: sealed boxes that hold an app and everything it needs to run, so it behaves the same here as it does on my laptop. Nothing is installed on the server itself, which means an app can be replaced or thrown away without leaving anything behind.

Some are simple. The weather and surf apps are one box each. Others are not: the CS2 price tracker is five - the website, a job that goes and fetches prices, a database, a cache, and a watchdog that restarts anything that dies overnight - and the Secure Package Registry runs its full ten-box production setup. All of it inside the same 2 GB.

Knowing When It Breaks

Every service on the droplet gets poked at regularly to check it still answers, and the results go straight to the status page linked at the top of this page. It's public on purpose: you can see for yourself whether anything is down instead of taking my word for it. A separate dashboard gives me a view of all the containers for a quick look or a restart.

The water API is the exception, because uptime checks would lie about it. A scheduled job that quietly stops running still answers requests perfectly happily, so the service would look healthy while the data behind it went stale. It reports on its own last collection instead, publicly, at /health.

Keeping People Out

The firewall sits in front of the machine, in DigitalOcean's network rather than on the server itself, and turns away everything that isn't on a short list: remote access, web traffic, mail and the VPN. In front rather than on it for a specific reason. When Docker opens a port for a container it edits the server's own firewall rules to do it, and can end up quietly waving through traffic the host firewall believes it is blocking. A firewall the server can't edit doesn't have that problem.

After that it's layers. Databases can't be reached from outside at all. Admin pages need a login or the VPN. Remote access is by cryptographic key only, never a password, so there is nothing to guess. The mail server throttles repeated failed logins by itself, turning away something like 5,000 guessing attempts a day without ever getting in the way of a real one.

1001. At the Edge

Cornish Water Watch API

A public record of the storm overflows discharging on the Cornish coast. Everything else on this page runs on the droplet. This does not, and the collector is the reason.

It has to fire every fifteen minutes, forever. Miss a window and that data is gone for good, because the source feed reports the current state only and there is nothing to go back and re-read. The droplet is a 2 GB box that is already running a mail server. One out-of-memory kill, or one reboot during an upgrade, and there is a hole in the record that nobody can fill in afterwards.

Up here the schedule is Cloudflare's problem instead of mine, D1 holds the history, and at this volume it costs nothing. That leaves my own code as the only thing that can go wrong, so every run is logged and the last one is public at /health. A dead job should not be able to pass for a quiet week with no spills.

The Site Itself

A portfolio site is the one thing here with no excuse for ever being down. So this one is not an application. It is a folder of files copied into a Cloudflare bucket: hand-written HTML, CSS and JavaScript, no framework, no build step, nothing running. If the droplet has a bad day, this page does not notice.

The deploy script is the only moving part, and most of it is there to defeat caching. Every stylesheet and script link gets stamped with the time it went up, because the alternative is a visitor being handed today's page with last week's stylesheet. Then it mirrors the folder into the bucket and clears the cache.

Images go up as WebP and the originals stay in the repository without being published, which is the difference between the homepage pulling 1.5 MB and pulling 275 KB.
